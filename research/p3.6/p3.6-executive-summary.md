# Phase P3.6: Standalone Mode B Discovery & Feasibility — Executive Summary

## 1. Project Context & Investigation Mandate

In Phases P3.1–P3.5, the Antigravity Android Port achieved **Mode A: Paired Desktop Hub Architecture**. The Android application connects via TLS/HTTP to an active desktop Antigravity `language_server.exe` daemon, providing 100% genuine access to original Google Cloud Code models (`Gemini 4 Argon High/Med`, `Claude Sonnet 5.5`), authenticated Google user profiles (`Bean Bag`, `monsterbag293@gmail.com`), Pro subscription entitlements, real-time Cortex trajectory streaming, and desktop SQLite persistence.

The mandate of **Phase P3.6** is to investigate the technical and legal feasibility of **Mode B: Fully Standalone Original Antigravity on Android**:
> An Android APK that contains everything it legitimately can to operate independently without requiring a desktop computer, a paired laptop, a separately operated server, or paid third-party hosting, while preserving the genuine original Antigravity agent experience.

---

## 2. Key Discoveries

Our systematic investigation yielded four major architectural and technical discoveries:

### 2.1 The Native Language Server Daemon (`language_server`)
By inspecting the 187 MB binary `language_server.exe` (built at Google3 `CL: 1015941558` on branch `antigravity_web_release_branch`), we uncovered its comprehensive command-line interface. Key flags include:
- `-standalone=true`: Provisions an embedded HTTPS web server on `127.0.0.1` hosting the complete built-in web UI and Connect-RPC/gRPC-Web API.
- `-web_bundle_path=""`: Allows serving an external compiled web UI bundle.
- `-model_api_client_type=ccpa`: Supports both Google internal Cloud Code (`ccpa`) and public Gemini API (`gemini`).
- `-cloud_code_endpoint=""`: CCPA API URL configuration.
- `-generative_service_addr="blade:google.ai.generativelanguage.v1main.generativeservice-prod"`: Internal Stubby address for generative AI calls.
- `-persistent_mode=true` and `-subclient_type="hub"`: Background daemon lifecycle management.
- Google distributes official multi-platform binaries via `storage.googleapis.com/antigravity-public/` for:
  - `darwin-arm64` (Apple Silicon)
  - `darwin-x64` (Intel macOS)
  - `linux-x64` (Standard x86_64 Linux)
  - `linux-arm64` (ARM64 aarch64 Linux)
  - `windows-x64` (Windows PE)
  - **No Android/Bionic build exists.**

### 2.2 Google's Official Cloud Infrastructure: Remote Agents vs Remote Control
Google's web platform at `antigravity.google.com` separates remote capabilities into two distinct architectures:
1. **Remote Control**: Tunnels a web browser back to the user's local desktop workstation running the Antigravity desktop app or `agy` CLI. (Equivalent to Mode A; requires a powered-on desktop computer).
2. **Remote Agents**: Runs agent sessions, terminal commands, and tool execution inside isolated, Google-managed cloud virtual machines without needing a local host machine.
   - **Crucial Finding**: Remote Agents is **strictly a paid feature** restricted to **Google AI Pro ($19.99/month)** and **Google AI Ultra ($99.99/month)** subscriptions. It is completely unavailable on the Free Individual Tier ($0/month).
   - Furthermore, the communication protocol is private, session-cookie-authenticated, and not exposed via any public third-party client API.

### 2.3 Community Self-Hosting: `AFSlayer/antigravity-server`
The open-source project `AFSlayer/antigravity-server` (Antigravity Remote) provides a Go reverse proxy wrapping `language_server --standalone`:
- It downloads official Linux binaries directly from `storage.googleapis.com/antigravity-public/` without redistributing proprietary code.
- It runs on headless Linux servers (e.g., Oracle Cloud Free Tier, AWS, DigitalOcean) using Caddy for TLS and PBKDF2 for password authentication.
- **Limitation**: It is not a standalone agent engine; it is merely an HTTP/HTTPS proxy. It requires a separately operated Linux machine or VM and cannot eliminate external infrastructure.

### 2.4 The Android OS Execution Barrier (Bionic, W^X, and TCMalloc)
Attempting to run Google's `linux-arm64` binary directly inside Android encounters multiple hard OS barriers:
1. **Dynamic Linker & Libc**: Google compiles for `glibc` (`/lib/ld-linux-aarch64.so.1`). Android exclusively uses **Bionic libc** (`/system/bin/linker64`). Direct execution aborts with `ENOENT`.
2. **SELinux W^X Restriction (Android 10+, API 29+)**: Writable application directories (`/data/data/<package>/`) are mounted `noexec`. Android apps targeting modern API levels cannot execute unpacked binary executables.
3. **Virtual Address Space Conflict**: `language_server` is linked with TCMalloc expecting a 48-bit virtual address space (`CONFIG_ARM64_VA_BITS_48`). Standard consumer Android kernels are compiled with 39-bit VA (`CONFIG_ARM64_VA_BITS_39=y`), causing TCMalloc to immediately abort with `SIGSEGV`.
4. **Missing Toolchain**: The Android app sandbox contains no standard developer utilities (`git`, `bash`, `node`, `python`, compilers) that the genuine Antigravity agent depends on to execute workspace actions.

## 4. Final Verdict & Classification

Based on exhaustive empirical and technical evaluation against the mandatory project requirements, Phase P3.6 formally classifies the standalone investigation as:

### **Category D — No Currently Viable Genuine Mode B**

**Why?**
No route currently satisfies all mandatory requirements simultaneously:
1. **Running locally in the APK** is technically blocked by Android OS kernel address space restrictions, SELinux execution policies, glibc/Bionic dynamic linking incompatibility, and the absence of a developer userland.
2. **Connecting to Google's official headless cloud backend (Remote Agents)** requires a mandatory paid Google AI Pro ($19.99/mo) or Ultra ($99.99/mo) subscription and relies on private, undocumented web session protocols.
3. **Running a self-hosted instance (`antigravity-server`)** requires the user to configure and maintain a separate Linux server or cloud VM, violating the zero-external-infrastructure requirement.
4. **Using public Gemini API** replaces the genuine Antigravity Cascade engine with a custom chatbot, directly violating the requirement for genuine original agent functionality.

### Recommended Path Forward
1. **Preserve Mode A (Paired Desktop Hub)** as the primary, authentic Antigravity experience. It delivers 100% fidelity, genuine Cloud Code models, authenticated Google Pro entitlements, and native workspace tool execution.
2. **Enhance Mode A Usability**: Streamline the pairing workflow (e.g., automated LAN discovery, QR code pairing, and ADB reverse over USB).
3. **Offer an Optional "Advanced Remote Hub" configuration** in Settings for power users who already operate a self-hosted `antigravity-server` or cloud VM, without making it a mandatory hurdle for standard users.
4. **Retain Local Gemini Fallback** as a clearly labeled, isolated offline compatibility mode for basic mobile tasks.
