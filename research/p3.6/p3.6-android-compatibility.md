# Phase P3.6: Android Runtime & Binary Compatibility Analysis

## 1. Executive Summary

This document details the low-level operating system, binary, runtime, and native library barriers that prevent running Google's original Antigravity `language_server` binary natively inside an Android application.

While both standard Linux and Android utilize the Linux kernel, Android's user space, security architecture (SELinux), dynamic linker, C standard library (Bionic), and memory management differ fundamentally from desktop Linux distributions.

### 2.1 Dynamic Linker & Dynamic Library Incompatibility

Google's official `language_server` Linux binaries (distributed via `storage.googleapis.com/antigravity-public/`) are compiled using Google's internal Google3 toolchain for standard desktop Linux distributions (Debian/Ubuntu/glibc).

#### The ELF Interpreter Header
When a 64-bit Linux ELF executable is executed via `execve()`, the Linux kernel inspects the program header `PT_INTERP` to determine which dynamic linker to invoke:
- **Standard Linux ARM64**: `/lib/ld-linux-aarch64.so.1`
- **Standard Linux x86_64**: `/lib64/ld-linux-x86-64.so.2`
- **Android ARM64 (AArch64)**: `/system/bin/linker64`
- **Android 32-bit ARM**: `/system/bin/linker`

On an unmodified Android device:
1. The path `/lib/ld-linux-aarch64.so.1` **does not exist**.
2. Root filesystem `/` is mounted read-only (`ro`) on production Android devices (Android 10+ Dynamic System Partitions / `system-as-root`). Symlinks cannot be created at `/lib`.
3. If an Android application attempts `ProcessBuilder(binaryPath).start()` on a glibc ELF binary, the kernel fails at the `execve()` system call with:
   ```
   java.io.IOException: Cannot run program "...": error=2, No such file or directory
   ```
   Even though the binary file itself exists, the missing ELF interpreter triggers `ENOENT`.

#### Bionic Libc vs GNU C Library (glibc)
Even if the dynamic interpreter could be redirected to `/system/bin/linker64`, Android's C library is **Bionic**, not **glibc**:
- Bionic deliberately omits large parts of the POSIX and GNU specifications to minimize memory footprint.
- Bionic does not support GNU symbol versioning (`GLIBC_2.17`, `GLIBC_2.34`, etc.).
- Critical data structures (`pthread_t`, `sigaction`, `stat`, locale structures) have incompatible binary layouts between glibc and Bionic.
- Attempting to load a glibc binary with Android's linker causes linker resolution failures and immediate process termination.

### 2.2 SELinux W^X Security Policy (Android 10+, API 29+)

To protect mobile devices against arbitrary code injection and malware, Android 10 introduced strict **W^X (Write XOR Execute)** policy enforcement for all applications targeting API level 29 or higher.

#### SELinux Denial on App Data Directory
In standard Android applications, files extracted from the APK (e.g., from `assets/`) are written to the application's internal data directory:
`/data/data/<package-name>/files/` or `/data/user/0/<package-name>/files/`.

On all modern Android versions (Android 10, 11, 12, 13, 14, 15):
- The filesystem is mounted with the `noexec` flag, or SELinux policies deny the `execute` permission on files labeled `app_data_file`.
- When an app attempts to execute a binary from this directory, SELinux blocks the call:
  ```
  type=1400 audit(0.0:123): avc: denied { execute } for comm="ProcessBuilder"
  path="/data/data/dev.agentic.antigravity/files/language_server"
  scontext=u:r:untrusted_app:s0:c123,c456
  tcontext=u:object_r:app_data_file:s0:c123,c456 tclass=file permissive=0
  ```
- The Java invocation throws:
  ```
  java.io.IOException: Cannot run program "...": error=13, Permission denied
  ```

#### Why Packaging as `.so` in `jniLibs` Does Not Solve This
Some developers attempt to bypass W^X by renaming executable binaries to `lib<name>.so` and placing them in the APK's `jniLibs/arm64-v8a/` directory, which Android extracts into the read-only `/data/app/<package>/lib/arm64/` directory.

However:
1. Files extracted into `nativeLibraryDir` can only be loaded dynamically via `dlopen()`. They cannot be invoked as standalone executables via `execve()` on modern Android without triggering SELinux denials.
2. Even if `dlopen()` is called, `language_server` is an executable binary with a `main()` entry point and glibc dynamic dependencies, not an Android JNI shared library (`JNI_OnLoad`). Loading it via `dlopen()` fails with `unresolved symbol` errors.

### 2.3 Kernel Virtual Address Space Conflict: 39-bit vs 48-bit VA

One of the most insidious technical barriers discovered in our investigation involves the virtual memory allocator used in Google3 binaries.

#### TCMalloc Address Space Assumptions
Google's server software, including `language_server`, is built using **TCMalloc** (Thread-Caching Malloc). In 64-bit ARM Linux server builds, TCMalloc relies on pointer tag packing and virtual address layout algorithms that explicitly assume a **48-bit Virtual Address (VA) space** (`256 TB` user space virtual memory):
```
48-bit VA: 0x0000_0000_0000_0000 to 0x0000_FFFF_FFFF_FFFF
```

#### Android Kernel 39-bit VA Layout
On mobile devices, physical RAM typically ranges from 4 GB to 16 GB. To conserve kernel memory overhead (specifically, page table memory consumed by 4-level translation tables), many smartphone System-on-Chips (Snapdragon, Exynos, MediaTek, Tensor) configure their ARM64 Linux kernels with:
```
CONFIG_ARM64_VA_BITS_39=y
```
This restricts the user space virtual address range to **39 bits** (`512 GB` user space virtual memory):
```
39-bit VA: 0x0000_0000_0000_0000 to 0x0000_007F_FFFF_FFFF
```

#### The Consequence
When a Google3 binary compiled with 48-bit TCMalloc assumptions runs on a 39-bit ARM64 kernel:
- During early C++ runtime initialization (before `main()` is even reached), TCMalloc attempts to map virtual address spans in high memory.
- The `mmap(2)` system call fails or returns an address outside the expected range.
- TCMalloc immediately aborts with:
  ```
  FATAL: TCMalloc address space mismatch / Virtual address allocator failed
  ```
  or triggers an uncatchable `SIGSEGV` / `SIGILL`.

This limitation exists at the **host Linux kernel level** and cannot be worked around in user space without running a full CPU/MMU emulator (such as QEMU).

### 2.4 Missing Host Developer Toolchain & Userland

The genuine Antigravity agent is an **autonomous software engineering agent**. Its core capabilities rely entirely on invoking host system commands to interact with codebases:

| Tool Invocation | Required System Binary | Present in Android APK? |
|---|---|---|
| Run terminal commands (`run_command`) | `/bin/bash` or `/bin/sh` with GNU coreutils | **NO** (Android only has limited `toybox`) |
| Inspect diffs and repositories (`git_diff`, `git_status`) | `/usr/bin/git` | **NO** |
| Run tests and builds (`run_tests`) | `python3`, `node`, `npm`, `gradle`, `cargo` | **NO** |
| Code formatting and linting | `prettier`, `black`, `eslint`, `gofmt` | **NO** |
| Process inspection and signals | `ps`, `kill`, `pgrep`, `lsof` | **NO** (restricted by SELinux app isolation) |

Even if `language_server` could magically execute on Android, the moment it attempts to invoke its built-in workspace tools, every command would fail because the underlying operating system does not possess a developer userland.

### 2.5 Android Process Lifecycle & Background Eviction

The Android operating system is designed to aggressively conserve battery and memory:

#### The Low Memory Killer (LMK)
- Any native process spawned by an application that consumes significant memory (the desktop `language_server` occupies between 400 MB and 1.5 GB of RAM when active) is prioritized for immediate termination by the kernel LMK when the user switches apps.

#### The Phantom Process Killer (Android 12+, API 31+)
- Android 12 introduced the **Phantom Process Killer**:
  - Monitors all child processes spawned by apps via `fork()` or `ProcessBuilder`.
  - Caps the total number of child processes system-wide to **32**.
  - Automatically kills child processes that consume CPU in the background or remain active when the parent app is paused.
- Running a persistent language server daemon as a background child process violates Android's process architecture and will be killed unpredictably by the OS.

## 3. Summary of Android Compatibility Audit

| Technical Dimension | Requirement for `language_server` | Android Platform Reality | Compatibility Status |
|---|---|---|---|
| **ELF Interpreter** | `/lib/ld-linux-aarch64.so.1` | `/system/bin/linker64` only; `/` is read-only | **FATAL INCOMPATIBILITY** |
| **C Standard Library** | `glibc` 2.34+ with symbol versioning | `Bionic` libc without glibc symbols | **FATAL INCOMPATIBILITY** |
| **Filesystem Execution** | Writable executable directory (`W+X`) | SELinux blocks execution in app data (`noexec`) | **FATAL INCOMPATIBILITY** |
| **Kernel VA Space** | 48-bit Virtual Address (`VA_BITS_48`) | Many Android kernels use 39-bit VA (`VA_BITS_39`) | **FATAL INCOMPATIBILITY** |
| **Host Tooling** | `git`, `bash`, `node`, `python`, GNU tools | Standard Android lacks all developer tools | **FATAL INCOMPATIBILITY** |
| **Process Lifecycle** | Unconstrained background daemon | Killed by LMK and Phantom Process Killer | **HIGH INSTABILITY** |

**Conclusion**: Running Google's original `language_server` binary natively inside an Android application APK is **technically impossible** on standard Android operating systems without modifying the host kernel, rooting the device, or running heavy full-system emulation.
