# Phase P3.6: Backend Options Investigation

## 1. Overview

This document provides a comprehensive technical audit of every conceivable backend option for achieving **Mode B: Standalone Antigravity on Android**. Each option is evaluated across its architecture, runtime requirements, network protocols, licensing constraints, and technical failure points.

### Option 1: Embedded Native `language_server` Binary inside APK (Route A)

#### Architecture
The 187 MB `language_server` ELF binary (built for `linux-arm64`) is bundled inside the APK assets or downloaded during first run, extracted into the app's private directory, and spawned as a local background daemon using `ProcessBuilder` or JNI `fork()`/`execve()`. The Android app connects to it via loopback TCP (`127.0.0.1:<port>`) using the `--standalone` flag.

#### Technical Requirements
- Linux ARM64 ELF executable.
- Dynamic linker `/lib/ld-linux-aarch64.so.1` and `glibc` 2.34+.
- 48-bit Virtual Address space for TCMalloc (`CONFIG_ARM64_VA_BITS_48`).
- Writable and executable filesystem directory (`W+X`).
- Child process lifecycle support without OS eviction.
- Standard developer toolchain (`git`, `bash`, `node`, `python`, compilers).

#### Failure Points & Blockers
1. **Dynamic Linker & Libc Incompatibility**: Android uses Bionic libc (`/system/bin/linker64`). It does not provide `glibc` or `ld-linux`. Direct execution fails immediately with `ENOENT: No such file or directory`.
2. **SELinux W^X Restriction (Android 10+, API 29+)**: Android enforces strict `W^X` policies on application private data (`/data/data/<package>/`). Attempting to execute an unpacked binary results in `java.io.IOException: error=13, Permission denied` (EACCES). Packaging the binary as a shared library (`.so`) fails because Android's dynamic linker cannot resolve glibc symbols.
3. **Kernel Virtual Address Space Conflict**: Many ARM64 Android kernels are compiled with 39-bit VA (`CONFIG_ARM64_VA_BITS_39=y`). TCMalloc expects 48-bit VA and immediately aborts on 39-bit kernels with `SIGSEGV` or `FATAL: address space mismatch`.
4. **Missing Dev Userland**: The Android sandbox contains only `toybox` with primitive commands. The genuine Antigravity agent cannot perform git operations, run scripts, execute tests, or install packages without an entire Linux distribution.
5. **Licensing & Redistribution**: Distributing Google's proprietary 187 MB binary violates Google's Terms of Service and copyright.

### Option 2: Google Official Cloud Backend — Remote Agents (`antigravity.google.com`) (Route B)

#### Architecture
Instead of running a local server or desktop machine, the Android frontend communicates with Google's managed cloud infrastructure at `antigravity.google.com`. The agent executes inside a secure Google Cloud VM provisioned with full Linux tooling, Git integration, and cloud workspace storage (Google Drive / GitHub).

#### Technical Requirements
- Google Account OAuth session with active Cloud Code / Beyond entitlements.
- Subscription: **Google AI Pro ($19.99/month)** or **Google AI Ultra ($99.99/month)**.
- Network connection to Google Cloud endpoints.

#### Failure Points & Blockers
1. **Mandatory Paid Subscription**: Remote Agents is **strictly disabled on the Free Individual Tier ($0/month)**. It requires a paid subscription ($19.99/mo minimum), violating the mandatory project requirement: *"No forced paid subscription"*.
2. **Private Proprietary Protocol**: Google does not publish an external client API or SDK for Remote Agents. Communication is conducted via internal web session cookies, Google-internal Beyond RPCs, and browser WebSockets that are tightly coupled to the `antigravity.google.com` web client.
3. **Workspace Access Boundaries**: Remote Agents cannot access local files stored on the Android device's filesystem; all work must be hosted in remote GitHub repositories or cloud storage.

### Option 3: Google Official Web Backend — Remote Control (Route B Variant)

#### Architecture
The user logs in at `antigravity.google.com` and connects to their local workstation via Google's secure tunneling relay.

#### Failure Points & Blockers
1. **Requires Powered-On Desktop**: Remote Control is explicitly designed to tunnel back to an active desktop computer running the Antigravity desktop app or `agy` CLI.
2. **Violates Core Requirement**: Fails the mandatory requirement: *"No desktop computer required"*.

---

### Option 4: Community Self-Hosted Backend — `AFSlayer/antigravity-server` (Route C)

#### Architecture
An open-source Go reverse proxy (`AFSlayer/antigravity-server`) runs on a headless remote Linux server (e.g., Oracle Cloud Free Tier, AWS, DigitalOcean, or home server). The proxy spawns `language_server --standalone`, injects PBKDF2 password protection, handles TLS certificate management via Caddy, patches mobile responsive viewports, and exposes the Connect-RPC/gRPC-Web endpoints over HTTPS.

#### Technical Requirements
- Remote Linux x86_64 or ARM64 VPS / server.
- Public IP address and domain name.
- Linux systemd daemon configuration.
- Automated installation script (`curl -fsSL https://raw.githubusercontent.com/AFSlayer/antigravity-server/main/scripts/install.sh | bash`).
- Downloads official binaries from `storage.googleapis.com/antigravity-public/`.

#### Failure Points & Blockers
1. **Requires Separately Operated Server**: The user must provision, configure, and maintain an external Linux server, violating the mandatory requirement: *"No separately operated server"*.
2. **Free VPS Friction**: While Oracle Cloud offers an "Always Free" tier, it requires credit card verification, has limited regional capacity, and involves complex Linux sysadmin setup (firewalls, ports, SSH keys) that standard mobile users cannot manage.
3. **Cannot Run Locally in APK**: `antigravity-server` is only an HTTP proxy for `language_server`. Embedding `antigravity-server` in the APK does not solve the underlying inability to run `language_server` on Android.

### Option 5: Official Developer SDK & CLI — `google-antigravity` / `agy` (Route D)

#### Architecture
Google distributes an official Python SDK (`google-antigravity`) on PyPI and a command-line harness (`agy`). These tools offer programmatic and terminal-based interfaces to the agent loop.

#### Technical Requirements
- Python 3.10+ runtime and CPython C-extension support.
- Platform-specific native binary wheel.
- Application Default Credentials (ADC) or Gemini API key.

#### Failure Points & Blockers
1. **Bundles Native Binary**: The Python SDK does not contain a pure-Python agent implementation. The wheel packages the same compiled platform-specific native binary (`language_server`) inside its distribution.
2. **Android Execution Blockers**: Running the SDK inside Android requires a full Python runtime (e.g. Chaquopy) and executing the embedded native binary, hitting the exact same glibc, Bionic, and SELinux W^X barriers as Option 1.
3. **Not a Client-Server Protocol**: The SDK is designed for script automation on developer machines, not as a remote gRPC-Web backend for the Jetski Web React frontend.

### Option 6: Public Generative AI API — Google AI Studio / Gemini API (Route D Variant)

#### Architecture
The Android app bypasses `language_server` entirely and routes requests directly to `generativelanguage.googleapis.com` using a public Gemini API key (the architecture implemented in P1.2/P1.3).

#### Technical Requirements
- Public Gemini API key (`AIzaSy...`).
- HTTP/REST or gRPC client.
- In-process Kotlin agent execution loop (`AgentRuntime`).

#### Failure Points & Blockers
1. **Not Genuine Antigravity**: The Gemini API provides raw LLM inference with basic tool-calling JSON declarations. It does not provide:
   - Genuine Cloud Code models (`Gemini 4 Argon High/Med`, `Claude Sonnet 5.5`).
   - The genuine Antigravity Cascade reasoning engine.
   - Genuine Google account session and Pro subscription tier integration.
   - Original desktop SQLite trajectory databases.
2. **Violates Mandatory Requirement**: The project brief explicitly commands:
   > *"A generic Gemini API integration is NOT equivalent to the original Antigravity agent runtime."*
   > *"Do not replace the original agent with a newly developed Gemini chatbot."*

### Option 7: Containerized / Emulated Android Subsystem — PRoot / QEMU in APK (Route E)

#### Architecture
Package a minimal Linux rootfs (Debian/Ubuntu arm64) along with PRoot or a CPU emulator (QEMU / Box64 / FEX-Emu) inside the APK. PRoot uses `ptrace(2)` to intercept system calls and simulate a standard Linux filesystem (`/lib`, `/usr`, `glibc`), allowing unmodified Linux binaries to run in user space.

#### Technical Requirements
- Native PRoot binary.
- Extracted rootfs (500 MB – 2 GB).
- Kernel support for `ptrace`.

#### Failure Points & Blockers
1. **Android 10+ SELinux ptrace Block**: On Android 10+ (API 29+), SELinux restricts `ptrace` between processes spawned by untrusted apps.
2. **Cannot Bypass 39-bit Kernel Address Space**: PRoot operates in user space; memory allocations are handled by the host Android kernel. On a 39-bit VA kernel, TCMalloc cannot be tricked into believing a 48-bit address space exists without full CPU/MMU emulation.
3. **Prohibitive Performance & Storage Penalty**: Emulating a 48-bit address space and GNU toolchain via QEMU results in a 10x–50x performance degradation, several gigabytes of storage overhead, extreme battery drain, and thermal throttling.
4. **App Store Policy Violations**: Distributing or downloading executable environments inside mobile apps violates Google Play Developer Distribution Agreement Section 4.9.

---

### Option 8: Ephemeral Cloud Shell Dev Environment — Google Cloud Shell (Route E Variant)

#### Architecture
Every Google account includes access to Google Cloud Shell: a free, web-hosted Debian Linux VM with 5GB persistent storage, pre-installed developer tools (`git`, `node`, `python`, `go`), and 50 hours of free weekly usage. A user could run `language_server` or `antigravity-server` inside Cloud Shell and connect the Android app to Cloud Shell's web preview port.

#### Technical Requirements
- Google account.
- Browser login to `shell.cloud.google.com`.
- Background execution script.

#### Failure Points & Blockers
1. **20-Minute Inactivity Timeout**: Google Cloud Shell strictly terminates sessions after 20 minutes of terminal inactivity. It is impossible to run a persistent background service without an active interactive browser window open.
2. **Weekly Quota Limits**: Cloud Shell caps usage at 50 hours per week.
3. **High User Friction**: The user must open a browser, log in to Cloud Shell, run terminal commands, set up tunneling, and refresh the session every 20 minutes. This violates the seamless mobile APK objective.
