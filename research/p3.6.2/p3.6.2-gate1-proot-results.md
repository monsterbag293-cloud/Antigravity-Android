# Phase P3.6.2 — Gate 1: PRoot Userspace Execution Verification on Physical Device

## 1. Executive Summary

This report documents the live empirical execution test of an unprivileged **PRoot ARM64 Linux userspace environment** on the physical **Google Pixel 10 Pro** (`blazer`), running **Android 17 (API 37)** with Linux kernel **6.6.127**.

The test confirms that:
1. A legitimate ARM64 PRoot executable operates with zero root access, zero SELinux modifications, and zero kernel alterations.
2. PRoot successfully intercepted system calls via `ptrace` and `seccomp_filter`, seamlessly remapping file paths and host devices.
3. Official Debian 12 (Bookworm) ARM64 glibc binaries (`uname`, `id`, `bash`, `dpkg`, text pipelines) executed with **exit code 0** and **zero standard error output**.
4. Tracing occurred cleanly under Android's standard SELinux `Enforcing` policy with **zero AVC denial events**.

## 3. Upstream PRoot Analysis & Android Packaging Architecture

### 3.1 Upstream Source & Compilation Model
- **Codebase**: Upstream PRoot (`proot-me/proot`) with Android adaptation forks (`CypherpunkArmory/proot` and `termux/proot`).
- **Dependencies**: Hierarchical memory allocator `libtalloc` (`libtalloc.so.2`), Bionic `libc.so`, and optional POSIX shared memory emulation (`libandroid-shmem.so`).
- **Mechanics**: Intercepts guest system calls using `ptrace(2)` and `PR_SET_SECCOMP` (`seccomp_filter`). System calls modifying or querying filesystem paths (`openat`, `stat`, `execve`, `readlink`) are rewritten to map into the guest root filesystem.

### 3.2 Executable vs Shared Library Architecture
Android application security (Android 10+, API 29+) enforces **W^X** (Write XOR Execute) on application writable storage (`/data/data/<package>/`). As a result, binaries cannot be directly executed from `/data/data/<package>/files/` using `execve`.

To respect this security restriction legitimately:
1. The PRoot artifact is an **ELF Position-Independent Executable (`ET_DYN`)** with an entry point (`e_entry = 0x15524`) and dynamic linker `PT_INTERP: /system/bin/linker64`.
2. It is **not** a standard passive shared library; calling `execve()` on a genuine non-executable `.so` lacking an entry point fails with `ENOEXEC` (Exec format error).
3. In production APK packaging, the executable is placed in `jniLibs/arm64-v8a/libproot.so`. Android's package manager extracts files matching `lib*.so` into `nativeLibraryDir` (`/data/app/.../lib/arm64/`), which is explicitly granted read and execute (`rx`) permissions by SELinux.

## 4. Empirical Test Methodology & Results

### 4.1 Host Baseline Test (Without PRoot)
To verify that Debian glibc binaries cannot execute directly on Android host without user-space translation, the Debian `uname` binary was invoked directly:
```bash
/data/local/tmp/proot_test/rootfs/usr/bin/uname
```
- **Exit Code**: `126`
- **Standard Error**: `/system/bin/sh: ... No such file or directory`
- **Root Cause**: The ELF binary specifies GNU interpreter `/lib/ld-linux-aarch64.so.1`, which does not exist in Android host root (Android provides `/system/bin/linker64`).

### 4.2 Minimal Debian 12 ARM64 Environment Staging
- **Base Rootfs**: Official Debian 12 (Bookworm) ARM64 slim rootfs (`minbase`), sourced from Debian Docker maintainers (`debuerreotype/docker-debian-artifacts`).
- **Archive Size**: `28,144,358` bytes (~28.1 MB).
- **Cryptographic Hash**: SHA-256 `2d66c782e4847b8495b17a4b86be1159aa13d140fe4fd17cb1d536953d5114c6`.
- **Extraction Path**: `/data/local/tmp/proot_test/rootfs/`.

### 4.3 Command Execution Under PRoot

#### Test 1: `uname -a` (System identification)

## 5. Security & SELinux Policy Verification

During and immediately following all test executions:
- `logcat -d | grep -i avc` was inspected.
- **Result**: Zero SELinux denials for PRoot, ptrace, or unprivileged child execution.
- Under Android's `domain shell` and `untrusted_app` SELinux domains, `ptrace` between processes with identical UIDs is explicitly permitted.
- The device remains 100% unrooted, unmodified, and operating under SELinux `Enforcing`.

**GATE 1 PASS**: An unprivileged PRoot ARM64 Linux compatibility environment successfully executes on the physical Pixel 10 Pro under Android 17 / API 37 with zero security compromises. All prerequisite userspace capabilities are fully operational.
