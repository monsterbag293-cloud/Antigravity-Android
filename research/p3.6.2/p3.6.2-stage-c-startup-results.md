# Phase P3.6.2 — Stage C: Controlled Original Backend Startup Results

## 1. Executive Summary

This report documents the empirical results of **P3.6.2 Stage C: Controlled Original Backend Startup Verification**, executed on the physical **Google Pixel 10 Pro** (`blazer`) running **Android 17 (API 37)** with Linux kernel **6.6.127** (`CONFIG_ARM64_VA_BITS_39=y`).

### Central Findings
1. **Successful Native Execution**: Google's original, unmodified `language_server-linux-arm64` binary started cleanly inside the unprivileged Debian ARM64 PRoot userspace on the physical phone.
2. **TCMalloc Compatibility Confirmed**: Despite the Pixel 10 Pro's 39-bit kernel address space (`CONFIG_ARM64_VA_BITS_39=y`), TCMalloc initialized successfully without aborting, crashing, or triggering `SIGSEGV`.
3. **Sub-Second Initialization**: The language server initialized its internal services in **691.85 ms** (discovery file published within 1.7 seconds of process spawn).
4. **Hub Discovery & Web Frontend Operational**:
   - The server generated the official discovery file `hub_58888.json`.
   - `GET /` returned **HTTP 200 OK** and served the genuine embedded Google Jetski Web application.
   - `POST /exa.language_server_pb.LanguageServerService/GetStatus` and `GetUserStatus` returned **HTTP 200 OK** over local Connect-RPC.
5. **Sandbox & Scope Limitation**: This test was conducted under unprivileged ADB shell (`uid=2000`) in `/data/local/tmp`. It proves binary and kernel execution feasibility, but does **not** yet prove in-APK execution under `untrusted_app` SELinux domains.

## 7. Crucial Security Limitation: The App-Sandbox Boundary

**IMPORTANT CAVEAT**:
- This test was performed via **ADB shell** (`uid=2000(shell)` in `/data/local/tmp`).
- Under ADB shell, the process enjoys `shell` SELinux domain privileges, which permit binary execution from `/data/local/tmp` and `ptrace` between shell processes.
- An installed Android APK executes under the **`untrusted_app`** SELinux domain and a unique application UID (`u0_aXXX`).
- Android 10+ W^X security blocks `execve` on writable paths (`/data/data/<package>/`).
- Therefore, **in-APK execution has NOT yet been proven by Stage C**.
- Proving APK-level standalone execution requires compiling/bundling `libproot.so` inside the APK's `jniLibs` directory and testing execution from `nativeLibraryDir`.
