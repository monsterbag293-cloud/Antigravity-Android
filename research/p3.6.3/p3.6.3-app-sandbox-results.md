# Phase P3.6.3: Android Application Sandbox Execution Verification Results

## 1. Executive Summary

This report documents the empirical proof that **PRoot ARM64 Linux user-space virtualization executes natively inside the restricted Android Application Sandbox** (`untrusted_app_34` SELinux domain) on a physical, non-rooted **Google Pixel 10 Pro** (`blazer`) running **Android 17 (API 37)** with Linux kernel **6.6.127**.

This resolves the critical architectural question left open by Phase P3.6.2:
> *Can an unprivileged Android APK launch PRoot and trace Linux child processes under its own private application UID and SELinux domain without triggering W^X violations or ptrace denials?*

### Definitive Answer: YES.
- **APK Package**: `dev.agentic.proot.diag` (isolated diagnostic application).
- **Execution Identity**: UID `10383` (`u0_a383`), Domain `u:r:untrusted_app_34:s0:c127,c257,c512,c768`.
- **W^X Compliance**: PRoot and helper loader packaged into `jniLibs` as executable shared objects (`libproot.so`, `libproot_loader.so`, `libtalloc.so`). Android's package manager extracted them to `nativeLibraryDir` with `-rwxr-xr-x` and SELinux label `apk_data_file:s0`.
- **Private Storage Isolation**: Debian 12 ARM64 rootfs extracted from the APK asset directly into the app's private sandbox (`/data/user/0/dev.agentic.proot.diag/files/rootfs/`) in **599 ms**.
- **Child Tracing & Commands**:
  - `libproot.so --version`: Exit code `0` (7 ms).
  - `uname -a`: Exit code `0` (41 ms), outputting `Linux localhost 6.6.127-... aarch64 GNU/Linux`.
  - `id`: Exit code `0` (52 ms), outputting `uid=10383 gid=10383`.
  - `id -0`: Exit code `0` (41 ms), outputting `uid=0(root) gid=0(root)`.
  - Shell pipeline (`cat /etc/debian_version && uname -m && tr`): Exit code `0` (103 ms), outputting `12.15`, `aarch64`, `app_sandbox_success`.
- **Lifecycle & Process Control**: Spawned background processes terminated cleanly with exit code `0`; activity backgrounding (`KEYCODE_HOME`) and foreground resumption worked without process crashes or orphans.
- **SELinux Audit**: **Zero AVC denials for ptrace or execute_no_trans**.

## 2. Sandbox Security Architecture & W^X Compliance

### 2.1 The Android 10+ W^X Challenge
Under Android 10+ (API 29+) and Android 17 (API 37), the kernel's SELinux policy enforces:
`neverallow untrusted_app_all app_data_file:file execute_no_trans;`
Any attempt by an application targeting SDK 29+ to invoke `execve()` on a binary residing in `/data/data/<package>/` (which carries the `app_data_file` label) is immediately blocked by the kernel with `EACCES` (Permission denied).

### 2.2 The Native Library Packaging Solution
Android permits execution of binaries residing in the application's read-only native library directory (`nativeLibraryDir`), which carries the SELinux label `apk_data_file:s0`:
`allow untrusted_app_all apk_data_file:file { execute open read getattr execute_no_trans };`

To exploit this legitimate, documented Android mechanism:
1. **Executable Shared Object**: `libproot.so` is an ELF Position-Independent Executable (`ET_DYN`) with an entry point and `PT_INTERP: /system/bin/linker64`.
2. **Library Renaming**: The helper binaries were packaged into `jniLibs/arm64-v8a/`:
   - `libproot.so` (285,336 bytes)
   - `libproot_loader.so` (18,520 bytes)
   - `libtalloc.so` (44,552 bytes)
3. **Packaging Configuration**: In `build.gradle.kts`:
   ```kotlin
   packaging {
       jniLibs {
           useLegacyPackaging = true
       }
   }
   ```
   This directive instructs Android's package manager (`pm install`) to extract the libraries to disk rather than mapping them uncompressed within the APK zip.
4. **Linker Dependency Resolution**: `libproot.so` was patched at build time so its `DT_NEEDED` entry references `libtalloc.so` instead of `libtalloc.so.2` (preserving byte length), allowing Android's Bionic linker to locate it directly in `nativeLibraryDir`.

### 2.3 Verified On-Device Native Library Extraction
Captured via `ls -laZ` on the installed APK directory:
```text
-rwxr-xr-x 1 system system u:object_r:apk_data_file:s0 285336 1981-01-01 01:01 libproot.so
-rwxr-xr-x 1 system system u:object_r:apk_data_file:s0  18520 1981-01-01 01:01 libproot_loader.so
-rwxr-xr-x 1 system system u:object_r:apk_data_file:s0  44552 1981-01-01 01:01 libtalloc.so
```
All binaries were granted execute (`rx`) permissions natively by the operating system.

## 5. SELinux Audit & Diagnostics

During APK execution, `logcat` was audited for AVC denial events involving `dev.agentic.proot.diag` and `untrusted_app`:

### Denials Observed:
1. `avc: denied { read } for name="osrelease" dev="proc" scontext=u:r:untrusted_app_34...`
   - **Analysis**: Standard Android 14+ privacy hardening restricting access to `/proc/sys/kernel/osrelease`. Silently handled by application fallback.
2. `avc: denied { link } for name="perl" ... tclass=file`
   - **Analysis**: Toybox `tar` attempted to create a hardlink during unpack. Standard Linux file permissions and symlinks were preserved; zero functional impact.
3. `avc: denied { search } for name="tests" dev="dm-67" tcontext=u:object_r:shell_test_data_file:s0`
   - **Analysis**: PRoot scanned directory hierarchies and encountered a leftover `/data/local/tmp` artifact owned by ADB shell. PRoot skipped it cleanly without error.

### Critical Positive Security Findings:
- **Zero `avc: denied` for `ptrace`**: In Android's SELinux policy, `untrusted_app` domains are explicitly permitted to `ptrace` child processes within their own domain and UID.
- **Zero `avc: denied` for `execute_no_trans`**: Because `libproot.so` was loaded from `nativeLibraryDir` (`apk_data_file:s0`), execution was 100% compliant with Android's W^X policy.
