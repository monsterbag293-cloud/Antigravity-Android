# Phase P3.6.1: Antigravity Backend Runtime Dependencies Audit

## 1. Executive Summary

This report audits the actual runtime dependencies of Google's `language_server` binary. It distinguishes between components required for backend startup and core conversational reasoning versus external tools invoked only during specific optional agent actions.

---

## 2. Dependency Audit Across Execution Stages

```
+-----------------------------------------------------------------------------------+
|                        Antigravity Execution Lifecycle Stages                     |
+--------------------------+----------------------------+---------------------------+
| Stage                    | Operations Performed       | External Binaries Needed  |
+--------------------------+----------------------------+---------------------------+
| 1. Startup & Discovery   | Port binding, RPC setup    | NONE                      |
| 2. Cascade Conversations | Cortex reasoning, LLM chat | NONE                      |
| 3. Filesystem Operations | Read, write, diff, search  | NONE (Go native OS calls) |
| 4. Terminal Commands     | run_command tool           | /bin/sh (Rootfs bundled)  |
| 5. Git Version Control   | Commit, branch, diff       | git (Optional in rootfs)  |
| 6. Language Toolchains   | Execute user tests/scripts | python/node (Optional)    |
+--------------------------+----------------------------+---------------------------+
```

---

### Stage 1: Backend Startup & Initialization
When `language_server` is launched with `--standalone`:
1. It reads local configuration files from `~/.gemini/antigravity/`.
2. It initializes its internal Go SQLite database engines for trajectory and conversation tracking.
3. It binds to local TCP ports (HTTP on `57734`, HTTPS on `57733`).
4. It initializes its Connect-RPC and gRPC-Web dispatchers.
5. It publishes its discovery file (`hub_<port>.json`).

**External Dependencies**: **NONE**. The binary does not spawn any child processes or call external utilities during startup.

---

### Stage 2: Cascade Conversations & Cortex Planning
When a user initiates a conversation and interacts with the Cascade agent:
1. `SendUserCascadeMessage` receives user input over gRPC-Web.
2. The agent negotiates model generation with Google Cloud Code / Gemini endpoints over HTTPS using Go's built-in `crypto/tls` and HTTP/2 clients.
3. The cortex engine parses model thoughts, decomposes tasks, and plans steps.
4. Trajectory steps are streamed back to the client in real time.
5. All conversation history is written directly to the SQLite database (`conversations/<id>.db`) via compiled Go SQLite drivers.

**External Dependencies**: **NONE**. Core conversational reasoning, plan generation, and trajectory streaming operate entirely within the Go runtime.

---

### Stage 3: Workspace Filesystem Operations
When the agent executes file operations:
- `read_file`: Implemented via Go's `os.Open()` and `io.ReadAll()`.
- `write_file`: Implemented via Go's `os.Create()` and `os.WriteFile()`.
- Directory listing and pattern matching: Implemented via Go's `os.ReadDir()` and `filepath.Walk()`.

**External Dependencies**: **NONE**. All filesystem operations execute via standard POSIX system calls provided by the host kernel.

---

### Stage 4: Terminal Command Execution (`run_command`)
When the agent decides to execute a shell command:
- It spawns a child process using `/bin/sh` or `/bin/bash`.
- **In an Android PRoot environment**: The Debian rootfs includes standard GNU `/bin/sh`, `cat`, `ls`, `grep`, `sed`, `find`, and `awk`.
- The agent can execute standard shell scripts and commands seamlessly inside the rootfs.

---

### Stage 5: Git Operations (`git_diff`, `git_status`)
- If the open workspace is a Git repository, the agent may invoke `git` to inspect diffs or branch history.
- **Rootfs Availability**: The PRoot Debian rootfs can include the standard ARM64 `git` package (`apt install git`), occupying approximately 35 MB of disk space.

## 3. Dependency Classification Matrix

| Dependency | Purpose | Genuine Requirement Level | Provided by Android / Rootfs |
|---|---|---|---|
| **glibc 2.26+** | Dynamic linking runtime | **MANDATORY (Startup)** | **YES** (via PRoot Debian rootfs) |
| **libresolv.so.2** | DNS name resolution | **MANDATORY (Network)** | **YES** (via PRoot Debian rootfs) |
| **libpthread.so.0**| POSIX threading | **MANDATORY (Threading)** | **YES** (via PRoot Debian rootfs) |
| **`/bin/sh`** | Shell execution (`run_command`) | **TOOL-SPECIFIC** | **YES** (via PRoot Debian rootfs) |
| **`git`** | Version control tools | **OPTIONAL** | **YES** (Optional package in rootfs) |
| **`python3`** | Running user Python scripts | **OPTIONAL** | Optional package in rootfs |
| **`node`** | Running user JavaScript/Node tests | **OPTIONAL** | Optional package in rootfs |
| **Compilers (`gcc`)**| Compiling user C/C++ projects | **OPTIONAL** | Optional package in rootfs |

---

## 4. Conclusion on Runtime Dependencies

The assumption that `language_server` cannot run on Android because Android lacks developer compilers (`gcc`, `python`, `node`) is **factually incorrect**:
1. **Startup, networking, Cascade conversations, and file operations require ZERO external tools.**
2. Standard shell operations are fully satisfied by the minimal `/bin/sh` already included in a standard PRoot rootfs.
3. Complex language toolchains (`python`, `node`, `git`) are purely optional and only needed if the user specifically instructs the agent to execute code in those languages.
