## 3. Limitations (not verified — do not treat as done)

1. **No live Gemini run.** The E2E acceptance test scripts the model's tool calls. It proves the loop, tools, trajectory and diff plumbing, not that real Gemini produces valid calls with our declarations. Needs a run with a real API key.
2. **Not tested on-device/emulator.** Tests ran on the JVM on a Windows host. Android shell behaviour (`sh`, toybox), real `/data/user/0/...` paths, and the WebView rendering of the new live steps are unverified. Command tests exercised `cmd`, not `sh`; POSIX-only assertions were skipped on this host.
3. **`StreamAgentStateUpdates` JS decorator** (async-generator polling every 250 ms) has no automated test; only the Kotlin side is covered. The frontend's rendering of the new step payloads (`encodeStepJson`) is checked for field presence, not decoded by the real protobuf-es schema.
4. **Sandbox is not an OS sandbox.** It blocks listed binaries and `..` strings and sets cwd. A shell command can still reach outside the workspace by other means (absolute paths in arguments, `cd`). Treat `run_command` as high-risk; no user approval prompt exists yet.
5. `edit_file`/`write_to_file` diff counts are line-based approximations, not a real diff algorithm.
6. Model selection is limited to `gemini-2.5-flash` / `gemini-2.5-pro`; other frontend model ids are normalised to a default.
7. Test class has two Kotlin nullable-receiver compiler warnings (lines ~445, 455); harmless.
