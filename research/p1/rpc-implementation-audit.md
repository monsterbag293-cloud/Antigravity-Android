### Key Conclusions

1. **The UI Boots and Renders, but Agent Execution Is Single-Turn Text Chat Only:**  
   While `SendUserCascadeMessage` validates the user's Gemini API key via `KeystoreSecretStorage` and streams a single-turn text completion from `GeminiModelProvider` (`https://generativelanguage.googleapis.com/v1beta/models/...`), it **does not pass any `tools` (`functionDeclarations`)** in the Gemini API payload and **ignores `functionCall` response chunks**. Furthermore, the existing `:agent-runtime` (`AgentRuntime.kt`) and `:tools:local` (`LocalFileTools.kt`) modules are **completely disconnected** from `LanguageServerGrpcWebHandler.kt` and `MainActivity.kt`.
2. **Real-Time Agent Streaming Is Buffered by `shouldInterceptRequest`:**  
   Because `JetskiWebViewRequestInterceptor.shouldInterceptRequest` returns a synchronous `WebResourceResponse` backed by a `ByteArrayInputStream`, `SendUserCascadeMessage` blocks until the entire Gemini SSE response finishes, and `StreamAgentStateUpdates` returns a single-frame snapshot rather than pushing live token and tool-step deltas over an open server stream.
3. **Workspace File RPCs Have Protobuf Schema Mismatches and an Android POSIX URI Path Bug:**  
   `ReadDir` returns `{entries: [{name, isDir, sizeBytes}]}` instead of the protobuf `ReadDirEntry` schema (`{uri, fileType}`), and `StatUri` returns `{exists, isDir, sizeBytes}` instead of `StatUriResponse` (`{fileType, modTime, normalizedUri, size, content}`). In addition, `resolveSafeWorkspaceFile` (`LanguageServerGrpcWebHandler.kt:887`) calls `uriOrPath.removePrefix("file://").trimStart('/')`, which strips the leading `/` from Android POSIX `file:///data/user/0/...` URIs and causes `File(clean).isAbsolute` to evaluate to `false`.
4. **All State Is Volatile in Memory:**  
   Projects (`projects`), Cascade trajectories (`trajectories`), and Jetbox preferences (`themeMode`) live in in-memory `ConcurrentHashMap` instances inside `LanguageServerGrpcWebHandler` and are lost whenever the Android process restarts.

## 4. Detailed Audit of the 49 Handled RPC Methods Against the 6 Audit Criteria

Each of the 49 RPC methods currently matched in `LanguageServerGrpcWebHandler.dispatchRpc` (`lines 212–607`) was audited against six strict criteria:
1. **Intended Functionality:** Does it perform the real operation expected by Antigravity?
2. **Schema Compliance:** Does its JSON output match the exact protobuf field names, types, and enums in `language_server.proto`?
3. **Streaming Behaviour:** If `ServerStreaming`, does it push incremental updates over time or only return a one-shot snapshot?
4. **Error Handling:** Does it validate inputs and return appropriate gRPC status codes?
5. **State Maintenance:** Are changes reflected across related RPCs and persisted across app restarts?
6. **Frontend Compatibility:** Does the original `Jetski Web` UI consume the response without errors or silent drops?

## 5. Agent-Execution Pipeline Analysis

To achieve genuine Antigravity agent functionality in Phase 1, the backend must execute a complete, multi-step agentic tool loop rather than a single-turn text completion. Below is the end-to-end trace of how the original `Jetski Web` frontend interacts with `LanguageServerService` during a Cascade turn, compared against what currently exists in the Android backend.

```mermaid

    participant Handler as LanguageServerGrpcWebHandler
    participant Agent as AgentRuntime + Tool Loop (MISSING)
```

## 7. Android Compatibility Limitations

1. **`WebViewClient.shouldInterceptRequest` Streaming Limitation:**  
   Android's `shouldInterceptRequest` API requires returning a `WebResourceResponse` synchronously. Currently, `JetskiWebViewRequestInterceptor` runs `rpcHandler.handleGrpcWebRequest` synchronously into a `ByteArrayInputStream`. To push real-time multi-frame `StreamAgentStateUpdates` during a multi-step agent turn, we must either:
   - Use a `PipedInputStream` / `PipedOutputStream` inside `WebResourceResponse` (without `x-antigravity-grpc-web-b64`, or with chunked JS stream reading), **or**
   - Deliver live server-streaming frames from Kotlin to the JavaScript `fetch` decorator via `WebView.evaluateJavascript` / `WebMessagePort` into the open `ReadableStream` controller already created in `JetskiBundleLoader.kt`! *(Note: The `ReadableStream` controller is already instantiated in `JetskiBundleLoader.kt` lines 335–350 for the 6 open streams — wiring a Kotlin-to-JS push callback into that `ReadableStream` controller is clean, zero-latency, and bypasses `shouldInterceptRequest` buffering completely!)*
2. **Android App Sandbox & SELinux Process Execution (`RunCommand`):**  
   Android apps run as unprivileged UIDs under strict SELinux policy (`untrusted_app`). While `ProcessBuilder("/system/bin/sh", "-c", cmd)` works inside `workspaceRootDir` for standard POSIX utilities (`ls`, `cat`, `grep`, `find`, `sed`, `awk`, `cp`, `mv`, `rm`, `mkdir`), desktop toolchains (`node`, `python`, `git`, `cargo`, `gcc`) are not present in `/system/bin`. Therefore, core agent file/search operations **must** be implemented natively in Kotlin (via agent tools `view_file`, `write_to_file`, `edit_file`, `list_dir`, `grep_search`, `find_by_name`) rather than relying on shell commands, while `RunCommand` executes real `/system/bin/sh` commands via `ProcessBuilder` with clear sandbox reporting.
3. **Desktop Electron & Chrome CDP Subagent Incompatibility:**  
   RPCs that launch external desktop windows, attach to a desktop Chrome DevTools Protocol (CDP) port, or spawn x86_64 sidecar binaries (`SubscribeToSidecars`, browser automation RPCs) cannot run natively as desktop processes on Android.

## 8. Prioritised P1 Implementation Roadmap

Based on frontend usage in `main.js`, dependency ordering, and impact on genuine Antigravity usability, Phase 1 implementation is structured into five milestones (`P1.2` through `P1.6`):

### Milestone P1.2 — Genuine Multi-Step Agent Execution Loop & Real-Time Streaming (Highest Priority)
- **Objective:** Transform `SendUserCascadeMessage` from a single-turn text completion into a genuine multi-step Antigravity agent that plans, invokes tools (`view_file`, `write_to_file`, `edit_file`, `list_dir`, `grep_search`, `find_by_name`, `run_command`), records schema-valid `CortexTrajectoryStep` entries, and streams live step updates to the `Jetski Web` UI.
- **Scope:**
  1. **Extend `ModelProvider` & `GeminiModelProvider`:** Add Gemini `tools` (`functionDeclarations`), `functionCall` chunk parsing, `functionResponse` history turns, thinking extraction, and dynamic model selection (`gemini-2.5-flash`, `gemini-2.5-pro`) from `SendUserCascadeMessageRequest`.
  2. **Implement Multi-Step Tool Loop in `LanguageServerGrpcWebHandler` / `AgentRuntime`:** Execute up to `N` reasoning-and-tool iterations per user turn, creating and updating real `CortexTrajectoryStep` objects (`CORTEX_STEP_TYPE_VIEW_FILE`, `CORTEX_STEP_TYPE_LIST_DIRECTORY`, `CORTEX_STEP_TYPE_FILE_CHANGE`, `CORTEX_STEP_TYPE_GREP_SEARCH`, `CORTEX_STEP_TYPE_FIND`, `CORTEX_STEP_TYPE_RUN_COMMAND`, `CORTEX_STEP_TYPE_PLANNER_RESPONSE`).
  3. **Real-Time `StreamAgentStateUpdates` Push:** Wire live `AgentStateUpdate` frame emission from Kotlin to the open `ReadableStream` in `JetskiBundleLoader` (and support re-querying via `GetCascadeTrajectory` / `GetCascadeTrajectorySteps`) so tool calls and streaming tokens appear in real time during execution.
  4. **Implement `GetTurnDiff` & Real Cancellation:** Track per-turn file additions/deletions for `GetTurnDiffResponse` and wire coroutine `Job.cancel()` into `CancelCascadeInvocation` / `ForceStopCascadeTree`.

### Milestone P1.3 — Schema-Compliant Workspace Filesystem, Search & Project RPCs
- **Objective:** Fix existing filesystem bugs and implement the missing workspace/file/project RPCs called by `Jetski Web`.
- **Scope:**
  1. **Fix `resolveSafeWorkspaceFile` POSIX URI Bug:** Preserve leading `/` on `file:///data/user/0/...` URIs while maintaining strict canonical path-traversal protection inside `workspaceRootDir`.
  2. **Fix `ReadDir` and `StatUri` Protobuf Schemas:** Return `ReadDirEntry { uri, fileType }` (`FILE_TYPE_FILE`, `FILE_TYPE_DIRECTORY`) and `StatUriResponse { fileType, modTime, normalizedUri, size, content }`.
  3. **Implement Core File & Search RPCs:** `DeleteFile`, `MoveFile`, `CopyFile`, `CreateDirectory`, `FuzzyFind`, `CascadeGrep`, `FindDirectories`, `ValidateProjectPath`, `CreateProject`, `UpdateProject`, `DeleteProject`.

### Milestone P1.4 — Disk Persistence for Projects, Conversations & Jetbox State
- **Objective:** Persist all projects, Cascade trajectories, turns, steps, and `JetboxAppState` / `UserConfig` to disk inside `context.filesDir` so nothing is lost across app restarts.
- **Scope:**
  1. Persist `projects` and `trajectories` to structured JSON storage under `workspaceRootDir/.gemini/` or `context.filesDir/jetski_state/`.
  2. Implement `DeleteCascadeTrajectory`, `RenameCascadeTrajectory`, `UpdateConversationAnnotations`, and live push updates on `JetboxSubscribeToSummaries` and `ProjectUpdatesStream`.

### Milestone P1.5 — Sandboxed Android Shell & Terminal Execution
- **Objective:** Replace the mocked `RunCommand` handler with real sandboxed `ProcessBuilder("/system/bin/sh", "-c", ...)` execution inside `workspaceRootDir` with timeout, output capture, and cancellation (`KillCommand`, `GetActiveCommand`, `ReadTerminal`).

### Milestone P1.6 — Customizations: Skills, Rules, Workflows & Slash Commands
- **Objective:** Scan `workspaceRootDir/.gemini/skills`, `rules`, and `workflows` to populate `GetAllSkills`, `GetAllWorkflows`, `GetSlashCommands`, and `GetAgentScripts` with real workspace customizations.
