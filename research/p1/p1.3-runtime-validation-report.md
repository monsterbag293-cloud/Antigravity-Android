## 1. Root Cause Analysis

Inspection of the test execution traces, Gradle daemon logs, and XML test results revealed **three interacting causes**:

### Cause 1: Deprecated Model ID (`gemini-2.5-flash` returned HTTP 404)
The underlying API call failed on its first request with an HTTP 404 from `generativelanguage.googleapis.com`:
```json
{
  "error": {
    "code": 404,
    "message": "This model models/gemini-2.5-flash is no longer available to new users. Please update your code to use models/gemini-3.8-flash for the latest features and improvements. We recommend you to use the Interactions API (https://aistudio.google.com/docs/get-started).",
    "status": "NOT_FOUND"
  }
}
```
In P1.2, default model targets were hardcoded to `gemini-2.5-flash` in `GeminiModelProvider.kt`, `AgentRuntime.kt`, and `StageP13RealGeminiIntegrationTest.kt`. For new API keys, Google has deprecated `gemini-2.5-flash` and directs all callers to `gemini-3.8-flash`.

### Cause 2: Assertion Ordering Masked the API Error
In `StageP13RealGeminiIntegrationTest` (Test 1):
```kotlin
// Before fix:
println("[P1.3] REAL model=$model toolCalls=$events iterations=${out.iterationsUsed} final='${out.finalResponseText.take(200)}'")
assertTrue("Gemini produced no function call", events.isNotEmpty()) // FAILED HERE
assertEquals(null, out.errorMessage) // Never reached!
```
When the HTTP 404 error occurred, `AgentRuntime` caught the `IOException`, recorded it in `out.errorMessage`, and returned `events = []`. The assertion `events.isNotEmpty()` failed first, reporting `Gemini produced no function call` and masking the underlying HTTP 404 error.

In Test 2 (`SendUserCascadeMessage`):
The handler threw `GrpcWebProtocolException(UNAVAILABLE, "Model inference failed: Gemini API HTTP 404...")`, returning gRPC status 14. Because the RPC failed immediately, no trajectory steps were created and `agent-validation-summary.md` was never written.

### Cause 3: Protocol Correlation Flaw (Missing `id` on `functionResponse`)
In the Gemini REST v1beta specification for Gemini 3.8 / 2.0, when the model generates a `functionCall`, it assigns an `id` (e.g., `call_abc123`). The follow-up `functionResponse` turn **must include the exact matching `id`**:
```json
{
  "functionResponse": {
    "id": "call_abc123",
    "name": "list_dir",
    "response": { "success": true, "output": "..." }
  }
}
```
Previously, `GeminiModelProvider` discarded the model's `id` and generated a random local UUID, and omitted `id` when serializing `functionCall` and `functionResponse`. Additionally, explicit `toolConfig: { functionCallingConfig: { mode: "AUTO" } }` was omitted.
